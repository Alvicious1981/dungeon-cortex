## Objective
Extract or encapsulate the HUD action area into a reusable Action Bar while preserving existing action behavior.

Suggested component: `components/combat/ActionBar.tsx` (does not exist yet; this is the only declared future path).

## Repository facts (verified 2026-10-01 — re-verify in preflight)
- The action list is a constant in `components/combat/CombatHUD.tsx` (`F1` → `Attack`, `F2` → `End Turn`) next to the single
  `keydown` listener with text-entry and dialog guards. That listener is the shortcut authority.
- `MASTER_ARCH_GUIDE.md` §5.3: combat quick controls expose **only** backend-resolved `Attack` and `End Turn`. Today the bar
  therefore has two real actions. Other actions (spells, items, death saves) travel through `MacroDeck` and natural-language
  input; the bar must not duplicate or replace those paths.

## Baseline after PR #251 (verified 2026-10-01 against `f923082`)

Status: **Residual, and the premise changed.** See [UI-WORKFLOW.md](../UI-WORKFLOW.md) §3.1.

`components/combat/ActionBar.tsx` still does not exist. The action area is no longer in `CombatHUD`:
- `CombatHUD` keeps its `ACTIONS` constant (`F1` → `Attack`, `F2` → `End Turn`) **only for the keyboard lookup**. It renders
  no buttons, just a hint ("Atajos: F1 atacar · F2 finalizar turno") and its `children`.
- The buttons are `MacroDeck`'s combat group: "Atacar con arma" and "Finalizar turno", plus "Tirada de muerte" or "Esperar"
  when the player is downed. They map to `Attack`, `End Turn`, `Death Save` and `Wait`, and are disabled while any request
  is in flight (`transportBusy`).
- The single shortcut listener stays in `CombatHUD`; a bar must not add a second one.

So the extraction target is `MacroDeck`'s combat group, not the HUD. The maintainer should decide whether a separate Action
Bar is still wanted before this task runs: with two real actions, plus two for a downed player, the abstraction may no
longer pay for itself. If it runs, the rest of this file (slots from real data only, no invented actions, 44 px, accessible
names, one shortcut authority) still applies unchanged.

## Capability
Represent up to 10 slots conceptually. A slot exposes only data that actually exists:
- icon;
- label;
- shortcut;
- quantity;
- available / selected / disabled / pending / no-resource state;
- an empty state. An empty slot is not a tab stop and not a button.

Do not render slots for actions the backend does not resolve. A bar with two real slots is the correct result today.

## Compatibility
Preserve `F1 → Attack` and `F2 → End Turn` unless current `master` legitimately differs. **Do not duplicate keyboard
listener logic**: if the listener moves with the bar, move it; do not leave a second one behind.

## Accessibility
Every actionable slot is keyboard operable, has an accessible name, uses real disabled semantics, is at least 44×44 px, and
is not communicated by colour or icon alone (label or text alternative, plus the shortcut as text).

## Do not
- Implement hotbar drag customization unless a real existing contract already supports it.
- Add or change an action contract, a route or an event.
- Add a dependency.

## Targeted tests
Render, callback, shortcut, disabled, pending, quantity/empty states where supported, and the modal / text-entry protection.
Reuse `tests/components/combat-hud-keybinds.test.tsx` and add falsified tests for the bar.
Run with `pnpm exec vitest run --maxWorkers=2 <paths>`.
