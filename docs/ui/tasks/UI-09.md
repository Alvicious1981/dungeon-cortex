## Objective
Create a reusable Short Rest modal that presents existing mechanical authority.

## Repository facts (verified 2026-10-01 — re-verify in preflight)
- The authority is `lib/rules/rest-service.ts` (`resolveRest`). Its result carries `facts` (`RestFacts`): `hpBefore`, `hpAfter`,
  `hpRecovered`, `hitDiceSpent`, `hitDiceRecovered`, `hitDiceRemainingBefore`, `hitDiceRemainingAfter`, `exhaustionReduced`,
  `slotsRestored`, `hitDie`, `rolled`, `conMod`.
- Two entry points exist today: the action route (`actionType: "rest"`, emits `REST_COMPLETED`; `MacroDeck` offers
  "Tomar descanso corto") and `POST /api/campaign/[id]/rest` with body `{ "type": "long" | "short" }` (no UI component calls it yet).
- `resolveRest` accepts `hitDiceToSpend`, but **neither entry point lets the UI pass it**. With none named, the service decides
  how many Hit Dice a short rest spends. A Hit Dice *selector* therefore has no contract today.
- Short-rest recovery keeps changing in the backend (for example warlock Pact Magic slots refreshing on a short rest, #249).
  The UI renders what the response says; it never recomputes recovery.
- `AGENTS.md` records free-text rest parsing as a source of dormant defects. A structured control must not build a sentence and hope.

## Discover
Locate and read the real implementation and contracts for rest, short rest, Hit Dice, healing/recovery, spell and resource
recovery, the actions and APIs, and the tests. Choose the entry point in the plan and justify it. Prefer the existing correlated
lifecycle in `lib/events/action-transport.ts`; do not add a third path.

## Authority rule
Do not create a second rest-rules implementation. Consume the authority. Where a design element has no contract (the Hit Dice
selector above), do not fake it: show the available Hit Dice as information, or build the controlled presentational component
with the selection as an optional prop. Exposing `hitDiceToSpend` through the route or the action contract is a backend change:
`STOP-AUTHORITY`, separate task and Issue.

## UI
Support, using only data that exists:
- current / max HP;
- available Hit Dice;
- selected / spent Hit Dice, only where a contract supplies the choice or the result;
- preview or result when supplied;
- recoverable resources when supplied;
- confirm / cancel;
- a conditional Magical Recovery section, only when the real result or payload carries it.

## States
Initial, selection (only if real), processing, success, invalid, error — mapped onto `docs/UI_SPEC.md` §5. Invalid and error
states carry a textual explanation and a way forward (`StatusMessage`).

## Interaction
Keyboard, pointer and touch. A real modal: focus moves in, is trapped, returns on close; Escape cancels unless processing.
Global shortcuts stay inert behind it. No 3D dice.

## Targeted tests
Open/close, HP data, Hit Dice display (and selection only if real), cancel, confirm, processing, invalid, error, conditional
recovery section, keyboard and focus. Run with `pnpm exec vitest run --maxWorkers=2 <paths>`; falsify what you add.
