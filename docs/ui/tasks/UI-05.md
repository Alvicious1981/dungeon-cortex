# UI-05 — Ragdoll Equipment UI

## Branch
`claude/ui-05-ragdoll-equipment` (or the isolated non-master branch Desktop already created from `origin/master`).

## Prerequisite
UI-04 is present in `origin/master` (`git log origin/master --oneline --grep "^UI-04:"`). Otherwise `STOP-PREREQ`, unless the
START prompt records a maintainer deviation ([UI-WORKFLOW.md](../UI-WORKFLOW.md) §3).

## UI_SPEC anchor
`docs/UI_SPEC.md` §2 **P1.1**: inventory and equipment **as a list view**. The ragdoll is an enhancement of that, not a
replacement: the list view stays the primary accessible path, and the ragdoll never becomes the only way to see or change
equipment. Spatial editing is P2 and belongs to UI-06.

## Objective
Add a presentational equipment ragdoll integrated with the existing Character Sheet.

## Repository facts (verified 2026-10-01 — re-verify in preflight)
- `InventoryItem.equippedSlot` in `prisma/schema.prisma` holds `MAIN_HAND`, `OFF_HAND`, `ARMOR` or `ACCESSORY`; `null` means in
  the bag. The slot authority is `lib/rules/equipment-slot.ts`
  (design: `docs/superpowers/specs/2026-08-23-equipment-slot-authority-design.md`).
- Backend equipment rules are authoritative, including combat cost (`MASTER_ARCH_GUIDE.md` §4.4: body armour changes are refused
  in combat, shields cost an action, weapons and accessories use the free object interaction when available). The live equipment
  gate is in the campaign action route.
- An equipment sprite pack exists under `public/assets/sprites/equipment/` (usage: `docs/assets/SPRITES_USAGE.md`). It may supply
  icons if already served, but it is not required and not design authority (`docs/DESIGN.md` §7). The ragdoll must work with no
  illustration at all.

## Baseline after PR #251 (verified 2026-10-01 against `f923082`)

Status: **Delivered by #251 (equivalent).** Do not rebuild it. See [UI-WORKFLOW.md](../UI-WORKFLOW.md) §3.1.

`components/character/sheet/EquipmentTab.tsx` is the "Equipo" section of the character sheet:
- the four real slots (`MAIN_HAND`, `OFF_HAND`, `ARMOR`, `ACCESSORY`) around an illustrative silhouette from `md` up, and
  as plain rows on mobile; it works without any art;
- a backpack with text search and a category filter, a selectable item, and the item details that are actually stored;
- "Preparar equipar" only **prefills** `equipar <name>` in the action field through `prepareDungeonAction`; the player
  submits it and the server decides (`lib/ai/intent.ts` recognises `equipar`);
- keyboard operable: real buttons with `aria-pressed` and `aria-controls`; the list view remains the accessible primary;
- covered by `tests/components/CharacterSheetEquipment.test.tsx`.

Not delivered, on purpose: the `valid target`, `invalid` and `disabled with a reason` states, because there is no backend
equip-legality or preview contract and the UI must not invent one; drag; slots beyond the four.

Treat the task as closed. Reopen it only if the backend first exposes equip legality or a preview, which is a backend task.

## Slots
The package proposed thirteen slots (Head, Shoulders, Cloak, Torso, Bracers, Gloves, Belt, Boots, Ring1, Ring2, Amulet,
MainHand, OffHand). **Adopt only slots the real domain model defines.** As of 2026-10-01 those are the four above. The others have
no schema, no slot authority and no rules behind them. If the design cannot be delivered without them, `STOP-AUTHORITY`: that
needs a backend decision and its own Issue, not a UI task.

## Domain boundary
The ragdoll must not independently decide AC, attunement, item legality, strength requirements, two-handed restrictions or any
other D&D rule. It receives resolved state and callbacks, and shows the backend's refusal reason as text.

## States
- empty;
- equipped;
- selected;
- valid target;
- invalid;
- disabled;
- textual reason where available.

Must work without a character illustration.

## Interaction
A conventional, keyboard-accessible equip/select mechanism built on the existing equip contract. Drag may be added only if
safe and never as the only essential interaction. No motion library.

## Missing wiring
If real equipment data or an equip callback is not available to the sheet, use an optional controlled presentational
contract with a fallback. Do not invent an API, a route or persistence.

## Targeted tests
Slots, empty/equipped, selection, disabled/invalid reason, keyboard path, Character Sheet integration and fallback.
Run with `pnpm exec vitest run --maxWorkers=2 <paths>`; falsify what you add.

## Acceptance
