# UI-10 — Long Rest Interface

## Branch
`claude/ui-10-long-rest-ui` (or the isolated non-master branch Desktop already created from `origin/master`).

## Prerequisite
UI-09 is present in `origin/master` (`git log origin/master --oneline --grep "^UI-09:"`). Otherwise `STOP-PREREQ`, unless the
START prompt records a maintainer deviation ([UI-WORKFLOW.md](../UI-WORKFLOW.md) §3).

## UI_SPEC anchor
Not classified in `docs/UI_SPEC.md` §2. This task adds no product scope: it presents rest mechanics the backend already owns.
It uses the §5 state set, §8 mechanical limits and `docs/DESIGN.md` §6 motion. Say so in the plan.

## Objective
Create the Long Rest confirmation / resolution / summary UI using real mechanical results.

## Repository facts (verified 2026-10-01 — re-verify in preflight)
- Same authority and entry points as UI-09: `lib/rules/rest-service.ts` (`resolveRest`), the action route's `REST_COMPLETED`, and
  `POST /api/campaign/[id]/rest` with `{ "type": "long" }`. Reuse what UI-09 settled on; do not add a third path.
- `RestFacts` supplies `hpBefore` / `hpAfter` / `hpRecovered`, `hitDiceRecovered`, `hitDiceRemainingBefore` / `hitDiceRemainingAfter`,
  `exhaustionReduced` and `slotsRestored` (a boolean). The result also carries `character.hp`, `character.maxHp` and
  `character.spellSlots`.
- **No in-game time or duration is supplied.** Do not show one. A per-level spell-slot before/after exists only if the UI already
  holds the pre-rest slots from the same authoritative source; otherwise show the resulting slots without a delta.
- Eligibility refusals come from the backend as errors (`RestServiceError`, HTTP 409 family). The UI shows the supplied message;
  it never decides eligibility.

## Discover
Locate the authority for Long Rest eligibility, HP, Hit Dice, spell slots, class resources, in-game time and the rest result, and
record which of them really exist today.

## Authority rule
The UI must not independently calculate recovery, duration or eligibility.

## Flow
1. confirmation;
2. start;
3. processing / resolution;
4. summary;
5. return to game.

## Summary
When supplied by the real result, show for each resource: name, previous value, resulting value and, where useful, the recovered
amount. Do not invent unavailable categories.

## Motion
Follow `docs/DESIGN.md` §6: short (140 / 220 ms), `transform` and `opacity` only, no delayed information, none under
`prefers-reduced-motion: reduce`.

## States
- confirmation;
- processing;
- success;
- error;
- ineligible, when supplied by the authority.

Use `StatusMessage` for errors and status where appropriate; map onto `docs/UI_SPEC.md` §5.

## Targeted tests
Confirmation and cancel, processing, success / error / ineligible, summary resources, the return callback, reduced-motion
behavior where testable, and accessibility (focus, `aria-live`). Run with `pnpm exec vitest run --maxWorkers=2 <paths>`; falsify
what you add.
